# 满级瓶子炮攻速光环 · TDD 主案例

本次新增功能来自玩家提出的设计。先移除已取消的太阳灼烧，再为瓶子炮光环写测试、执行失败、实现通过、重构并回归。游戏其余功能已经存在，本记录不声称整个项目从第一天起采用 TDD。

## 功能规则与设计决策

三级瓶子炮支援圆形半径 **160 像素**内的其他炮塔，边界包含在内，攻击速度乘 **1.25**。一级、二级没有光环，不自我加速。多座瓶子炮的光环仅取最高倍率，不相乘、不相加；两座满级瓶子炮可以互相支援。

| 攻击类型 | 获得加成后的行为 | 保持原值的属性 |
| --- | --- | --- |
| 瓶子炮、星星 | 更频繁发射追踪弹 | 单发伤害、溅射伤害、弹速与原目标实例 |
| 风扇、火箭 | 更频繁发射直线穿透弹 | 弹速、距离、每弹对每目标仅命中一次；风扇减速时长与倍率 |
| 太阳、弓箭 | 更频繁触发范围攻击 | 每次伤害、作用范围 |
| 月亮 | 更频繁施放范围减速 | 每次减速强度、持续时间及月亮优先规则 |
| 魔法球 | 连续激光每秒伤害提高 25% | 连续锁定、射程和失效条件 |

魔法球没有等待下一发的冷却，强行缩短间隔并不能增加输出。因此它使用 `基础 DPS × 等级伤害倍率 × 攻速倍率 × dt`。一级原为 60 DPS，光环内变为 **75 DPS**。这是一项明确的玩法映射，不是偷偷把弹速或全局游戏时间加快。

光环查询基于当前游戏中的炮塔列表。升级成功立即启用，出售立即失效，失败的升级不能启用；新关卡不会继承旧光环。准备、暂停、商店等原有停战逻辑仍控制实际攻击。

### 冷却进度的难点

`cooldown` 存的是尚未完成的基础攻击时间，而非加成后的一次性倒计时。每帧扣除 `dt × 攻速倍率`，每次开火补回等级对应的基础冷却。加入或离开光环不重置这个量。

以一级瓶子炮 0.6 秒冷却为例，首次开火后，先正常经过 0.2 秒，再受光环影响经过 0.16 秒，最后移除光环。已经完成的攻击时间为 `0.2 + 0.16 × 1.25 = 0.4` 秒，剩余应为 **0.2 秒**。测试在之后 0.1999 秒检查未开火，再推进 0.0002 秒检查恰好增加一发，能够抓出中途重置、瞬发及重复乘倍率的问题。

### Red — 先用用户可观察的行为固定规则

先创建 [专项测试](../../tests/test_bottle_aura_tdd.py)，此时还没有 `Game.attack_speed_for`，`Tower.update` 也不接受攻速参数。运行得到真实 `AttributeError` 和 `TypeError`。

此外，使用现有 `Game.update` 的集成测试直接验证战斗结果，不依赖新接口是否存在，真实失败如下。

```text
AssertionError: 24.0 != 30 within 7 places (6.0 difference)
AssertionError: 12.0 != 15 within 7 places (3.0 difference)
AssertionError: 'playing' != 'won'
```

含义依次是魔法球攻击 0.4 秒仍只有 24 点而非 30 点伤害、0.2 秒只有 12 点而非 15 点伤害，以及 7 HP 的最后一个敌人没有在 0.1 秒内被加成激光击败。这些失败直接证明功能尚未实现。

### Green — 最小可用实现

1. 在 Game 中扫描三级瓶子炮，查询范围内是否有其他来源，返回 1 或 1.25。
2. Game 更新每座塔时传入当前攻速倍率。
3. 周期攻击只对冷却的消耗速度乘倍率。
4. 持续激光把倍率映射为单位时间伤害收益。

此时不添加 UI，不改变测试预期。同样 22 项测试全部通过，保存输出和补丁。

### Refactor — 隔离规则、计时与表现

通过测试后再做这些整理。

- 把光环半径和倍率从 Game 中的常数移入 `config.TOWERS`。
- `Tower.aura_radius` 负责等级门槛，`Tower.supports(other)` 负责自身排除和圆形距离，供战斗与 UI 共享。
- `Game.attack_speed_for` 统一多来源取最高值，不保存容易在出售后残留的增益缓存。
- 激光显式使用真实 `dt` 与独立 `attack_speed` 参数计算 DPS，避免后续扩展激光计时器时误把持续时间一起加速。

测试文件保持完全相同。重构后再添加金色光环圈、受益塔提示和选中说明，然后运行全套 92 项测试。

## 22 项测试覆盖

| 分类 | 测试行为 |
| --- | --- |
| 光环来源 | 全部塔种与 1～3 级组合，只有三级瓶子炮提供光环 |
| 空间边界 | 恰好 160、超过 0.001、96/128 斜边、落在包围方形但不在圆内 |
| 接受者 | 全部八种炮塔可受益 |
| 自身与互助 | 不给自身加成，两座满级瓶子炮可以互相加成 |
| 来源竞争 | 两个来源不叠加，出售一个仍生效，全部出售恢复原值 |
| 动态变化 | 升级/出售立即生效，同时不篡改剩余冷却 |
| 异常操作 | 金币不足升级失败；已出售的接受者不再获得加成 |
| 生命周期 | 新 Game 不继承旧光环 |
| 周期边界 | 七种周期塔 × 三等级，缩短后的间隔前后各验证一次 |
| 中途变化 | 加入与移除光环保留已完成的冷却进度 |
| 空闲 | 长时间无目标不能积攒一串瞬发弹 |
| 连续伤害 | 魔法球三级伤害按时间与倍率正确积分 |
| 时间分割 | 激光在不同光环时间段的累计伤害与帧划分无关 |
| 激光锁定 | 不因更前方的怪兽抢目标，出范围停止，死亡清空 |
| 手动清障 | 激光锁定障碍同样享受 DPS 加成 |
| 飞行弹体 | 单发伤害、弹速、存活期、距离、溅射和减速参数不变 |
| 穿透结算 | 火箭/风扇单弹多次更新，每个敌人仍只扣一次血 |
| 范围与减速 | 太阳/弓箭单次群伤与半径不变，月亮两目标均为 58% / 0.8 秒 |
| 旧设定移除 | 太阳命中后敌人自行更新时间，不再产生灼烧伤害 |
| 真实战斗入口 | Game 确实传递加成，交换塔列表顺序结果相同 |
| 停战状态 | App 准备、暂停、波次间隙均冻结攻击，恢复后继续生效 |
| 死亡结算 | 加成激光击杀最后敌人，清锁定、奖励一次并正确胜利 |

“时间分割无关”的断言专门针对持续激光在相同加成时间段内的积分，不宣称整个游戏对任意大 dt 均完全等价。周期炮塔沿用逐帧开火模型，实际 App 把战斗细分为最多 1/60 秒一步，开火有最多一帧的时间量化。

## 运行和现场展示

在项目根目录运行以下命令。无需额外安装 pytest，使用标准库 unittest；测试用 SDL dummy 和内存数据库，不更改玩家存档。

```powershell
.\.venv\Scripts\python.exe -m unittest tests.test_bottle_aura_tdd -v
.\.venv\Scripts\python.exe -m unittest discover -v
```

`run_stage.py` 是本次记录真实日志的辅助脚本，已有记录不允许覆盖。每份日志包含 UTC 时间、命令、退出码和源码/测试 SHA-256。`snapshots` 保存执行各阶段时的源码证据，不是另外一套可直接启动的游戏。

若需要现场重放 Red/Green/Refactor，请复制项目到独立演示目录，在副本中先反向应用 `04-regression.patch`、`03-refactor.patch`、`02-green.patch` 回到 Red，再依次正向应用后两份补丁，每一步运行同一测试命令。最终正向应用 `04-regression.patch` 恢复 UI。不要在当前游戏目录覆盖代码制造失败。

这三份补丁已实际验证逆向后再正向应用，得到与当前源文件一致的文本。补丁统一使用 LF 换行；若副本中的文件是 CRLF，应先统一换行再应用。
